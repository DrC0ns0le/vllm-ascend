# Qwen3.5 c64 code update

This update adds code and coverage for a separate execution/validation pass, as requested. Its base is `e68251a74373b8a370abfee53e08fa6c99cc881b`. All changes are new logical commits; the base was not amended, rebased or squashed. The earlier [validation report](VALIDATION.md) records the previous c4 delivery, not results for this update.

## Kernel change

`mega_kernel.cpp` contains the exact six added lines from [huawei-csl/megagdn-pto 1ed3a073](https://github.com/huawei-csl/megagdn-pto/commit/1ed3a073cb8d6456c8ccda89b7e72ef82da2c2c2), adapted only for indentation. The new V→MTE2 set/wait dependency protects the transpose source UB before the next load, including the later beta transpose. `chunk_h.cpp` and all other device kernels are unchanged. Packed multi-sequence eligibility remains enabled; no speculative barrier or single-sequence restriction was added.

The existing cache key includes `mega_kernel.cpp`. A regression test now exercises removal/reinstatement of the new dependency against the actual source and checks that the old binary remains while a new path is selected. The compiler logs its command, selected `.so` path, binary SHA256 and cache-hit status. The numerical report also records the loaded path/hash. Actual old/new compiled binary hashes cannot be supplied without Bisheng; record those logs in the execution pass. Do not delete the whole cache.

## Serving defaults

| Setting | Default |
| --- | --- |
| Active-request scheduler ceiling | 64 |
| Scheduling token budget | 2048 |
| Maximum model length | 1536 |
| FULL decode ladder | 1, 2, 3, 4, 8, 16, 32, 64 |
| Additional B/D PIECEWISE buckets | 128, 192, 256, 384, 512, 768, 1024, 1536, 2048 |
| KV-cache bytes | 16106127360 (15 GiB), configurable |
| Model/runtime | BF16, TP1, DP1, MRV1, task queue enabled |
| Prefix/chunked prefill | Disabled; Mamba cache mode `none` |

The 15 GiB default follows the user's approximate earlier cache setting; it is not a measured capacity requirement or sufficient-memory guarantee. Set `--kv-cache-memory-bytes` to another suitable capacity. Alternatively, explicitly select `--gpu-memory-utilization` for automatic sizing. The options are mutually exclusive. No hidden override restores the former 0.95 allocation.

```bash
python benchmarks/qwen35_low_latency/serve.py D --execute
python benchmarks/qwen35_low_latency/serve.py B --max-num-seqs 32 \
  --max-num-batched-tokens 4096 --kv-cache-memory-bytes 16106127360 --execute
```

The launcher accepts request ceilings 1–64 and rejects a token budget below 1536 while chunked prefill is disabled. Non-ladder ceilings add one terminal decode descriptor, for example limit 5 adds FULL-5, because the upstream dispatcher filters descriptors above the configured request ceiling. The default c64 configuration has exactly eight decode sizes. Budget overrides include their terminal PIECEWISE bucket. A/C retain only FULL-decode captures.

vLLM retains sole responsibility for admission, batching, cache allocation and preemption. A c64 ceiling does not force 64 complete prompts into one step or guarantee 64 maximum-length requests fit in memory.

## Startup and warmup

The existing model profile pass prepares MegaGDN before graph capture. Kernel compilation remains synchronous and compile errors propagate. The launcher logs the requested switches/capacity and checks required CLI flags before execution; confirm the actual runtime configuration using the existing server configuration log.

After starting the server, a deployment readiness gate can use:

```bash
python benchmarks/qwen35_low_latency/warmup.py --ready-file /workspace/qwen-ready.json
```

It waits for the served model and sends a token-count-checked P64/O4 request before atomically writing the marker. Remove the previous deployment's marker before starting a new deployment. Keep traffic out of the service until this gate succeeds: the helper does not intercept the server's HTTP health endpoint or install a proxy. Its elapsed time is measured from helper invocation, so start it alongside server startup when collecting startup timing. Graph capture and compilation logs remain separate evidence.

## Separate execution pass

Start with the direct kernel suite, using a process deadline in the validation environment to detect hangs:

```bash
TASK_QUEUE_ENABLE=1 python benchmarks/qwen35_low_latency/numerical.py \
  --model /dev/shm/Qwen3_5-2B --seeds 1024 2048 4096 \
  --output /workspace/megagdn-packed.json
```

The suite includes all four critical reproductions, bounded Nseq=1/2/4/8/16/32/64 cases, fixed ragged layouts, seeded random layouts and previous single-sequence boundaries. It compares each sequence's output and state, then uses independent, transposed state caches with the existing recurrent decode custom op for 1/4/8 steps. Both paths receive identical decode inputs. Any fallback fails the numerical case; a baseline fallback cannot masquerade as a MegaGDN pass. Tolerances remain provisional screening limits, not application-quality acceptance.

Run graph-only B before D, and gate D serving validation on the direct numerical result. The examples below use the already running variant; repeat c1/c2/c4/c8/c16/c32/c64 as required:

```bash
python benchmarks/qwen35_low_latency/benchmark.py --variant B --suite production \
  --distribution wide --requests 512 --concurrency 64 --output /workspace/B-c64-wide
python benchmarks/qwen35_low_latency/benchmark.py --variant B --suite production \
  --distribution short-heavy --requests 512 --concurrency 64 --output /workspace/B-c64-short
python benchmarks/qwen35_low_latency/benchmark.py --variant B --suite production \
  --distribution ragged --requests 512 --concurrency 64 --output /workspace/B-c64-ragged
python benchmarks/qwen35_low_latency/benchmark.py --variant D --suite live \
  --distribution wide --requests 1000 --concurrency 64 --output /workspace/D-c64-live
```

Production runs use O4; live runs use seeded O3–O10 and submit a replacement individual HTTP request whenever one completes. These suites use `--requests` as their total count; `--repetitions` applies to the older grouped suites. Prompts use actual tokenizer IDs, rotate content at equal lengths, and verify returned prompt usage. Every attempted request is retained with status, token counts and timing. Failures appear in error rate and cause a nonzero exit after saving results. Success latency quantiles exclude failed attempts. Output comparisons reject files containing failed requests.

`metrics.jsonl` preserves timestamped raw `/metrics` snapshots, including any runtime-exposed running/waiting requests, cache usage and preemption counters. Missing endpoints are explicit errors. Use runtime/NPU monitoring for free memory, memory high-water mark and state-cache utilization where they are not exposed. `max_client_in_flight` is a client limit observation, not proof of resident or simultaneously scheduled requests.

In a separate DEBUG run, use `inspect_log.py` to tabulate actual `(mode, bucket, scheduled tokens, request count)` routes and MegaGDN selections/fallback reasons. Its selection fraction counts observed layer prefill calls, not unique requests. Client overlap does not prove mixed scheduling. Check the recorded 5→8, 9→16, 17→32 and 33→64 decode routes, arbitrary PIECEWISE totals, and repeated FULL↔PIECEWISE transitions. Keep DEBUG logging out of latency runs.
